# Sesi 26 Sep 2026 — Perbaikan Rantai Watchdog + Prune gocache

> Konteks: HP Rentjong dipakai 24/7 (9Router + freebuff-proxy + cloudflared + dropbear). Disk 5.5GB terisi 88–92%. Auto-prune sudah ada tapi ditemukan 3 masalah. Semua diperbaiki dan diverifikasi hari ini.

## Kronologi temuan

1. **Pemicu:** setelah update freebuff-proxy ke v1.19.2 (build Go 22 menit), disk naik ke 92%. Cleanup manual (hapus `gocache` 221MB + `nr-update` 30MB + `.new` + backup usang) → 88% (749MB free).
2. **Pertanyaan user:** "sudah ada script pembersih otomatis?"
3. **Audit:** ditemukan `92_prune_cache.sh` → `prune-loop.sh` → `prune-cache.sh` (loop 1 jam, 6 item). Tapi:
   - `prune-loop.sh` **sedang MATI** (tidak ada proses).
   - `gocache` (221MB) **tidak tercakup** prune.
   - `sup-watch` menulis `supervisor mati -> dinyalakan` **tiap menit** padahal supervisor hidup.

## Akar masalah (diagnosa T1–T7 di `test-chain.sh`)

- `pgrep -f '[s]upervisor.sh'` via `busybox chroot` dari konteks Magisk **selalu exit 2** (false-negative) — padahal dari konteks SSH/chroot normal (exit 0).
- Akibat: sup-watch mengira supervisor mati terus-menerus → mencoba spawn tiap menit (spawn-nya tidak jadi, jadi tidak ada duplikat), tapi **tidak pernah benar-benar mengawasi**.
- Supervisor v4 di HP sebenarnya SUDAH punya penjaga prune-loop, tapi karena supervisor sendiri tidak dijaga efektif, rantai bisa putus senyap (terbukti: prune-loop mati tanpa ada yang menyalakan).

## Pelajaran untuk sesi berikutnya

1. **Jangan pakai `pgrep` via chroot dari konteks Magisk** — pakai `busybox ps | grep "[p]ola"`.
2. Kalau audit rantai watchdog: cek TIGA level (host service.d → chroot supervisor → prune-loop), jangan hanya satu.
3. `gopath` (±780MB) JANGAN dihapus — itu cache toolchain Go, menghemat ±35 menit build berikutnya.
4. Backup file lama SEBELUM patch: `cp -p file file.bak.$(date +%Y%m%d)`.
5. Kirim skrip ke HP via base64 (pola repo ini) — hindari quoting hell PowerShell → SSH.
